# Observation Notes — v0.8.1

## 目的

v0.8.1を28件の注文探索コーパスに通し、観測器の性能を評価するのではなく、現在の観測境界を確認した。

## 観測された境界

### 1. H3は「注文全体の意味構造」ではなく局所的な表層関係

`資料とデータを確認して、結果を表示してください。` では、H3は `データを確認` と `結果を表示` を観測する。一方、`資料` と `確認` の関係を意味的に補完しない。

これは現在のH3の設計と一致する。H3は明示されたTARGET + 粒度の低い局所的な接続 + ACTIONの関係だけを観測する。

### 2. 複数TARGETの関係は観測しない

`資料とデータを確認` の `資料` が `確認` に対応するのか、`資料とデータ` 全体が `確認` の対象なのかは観測しない。

この関係を将来観測対象にする場合でも、「意味理解」ではなく、明示的な接続構造として仕様化する必要がある。

### 3. 引用文と実注文の区別は現在の観測対象外

`「資料を確認してください」という文について説明してください。` では、引用内部のREQUEST/ACTION/TARGETも観測される。

これは現仕様では、引用の実行スコープを意味的に解釈していないためである。現在は「REQUEST表現が文字列として存在した」という事実を観測する。

ここで引用を除外する処理を追加する場合は、単なる語彙追加ではなく「引用境界を観測対象とする」という仕様変更になる。

### 4. H5は否定を意味解釈しない

`認証情報ではありません。` は、外部ルール `認証情報` に一致するためH5がONになる。

これは意図した仕様であり、H5はルール式への一致だけを観測する。

### 5. H6/H7は他の注文部品と独立して現れる

不可視制御文字はH6、URLはH7として観測できる。これらはREQUEST/ACTION/TARGETとは別軸であり、同じ注文に同時に存在できる。

## 次の問い

1. H3を現在の局所関係のまま維持するか。
2. 引用・コードブロック・説明対象としての文を、別の観測対象として明示する必要があるか。
3. ReceiptにEvidenceの位置情報をどの程度見せると、人間が元の注文へ戻りやすいか。
4. ACTION/TARGETの順序を「語彙の出現順」で保持する現在の方式が、複数注文でも十分に自然か。

## 方針

この文書は「誤検出率」や「正解率」を評価するものではない。観測器が何を観測し、何を観測していないかを人間が確認するための探索記録である。
